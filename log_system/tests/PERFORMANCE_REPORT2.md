## 5. 结论

### 5.1 多线程加速比低（最高仅 1.36×）—— 核心瓶颈

从 1T → 16T，吞吐只提升了 1.36×，远低于理想的线性扩展。
- **根因**：[`AsyncWorker::Push`](../logs_code/AsyncWorker.hpp:33) 持有单把全局 `std::mutex`，多个生产者线程轮流争锁；消费者执行 `fsync` 期间（flush_mode=2），所有生产者都阻塞在 `cond_productor_.wait`，形成串行化屏障。
- **佐证**：p99 从 1T 的 3.74 μs 爆增到 16T 的 278 μs（74×），max 从 6 ms 到 80 s 级。

### 5.2 256B payload 吞吐反而高于 64B（1.17~1.22×）—— fwrite 聚合效应

- 64B 时每条日志净 payload 比例低，消费者 `RealFlush` 对同样大小 buffer 要处理更多次 fwrite 相关系统调用；
- 256B 时单次 fwrite 搬运的有效数据更多，CPU per-op 开销分摊，因此 ops/s 和 MB/s 双涨。

### 5.3 1024B payload 吞吐大幅下降（0.35× 单线程，0.26× 8线程）

- 单条 1024B 消费缓冲区更快，生产者更频繁进入 `cond_productor_.wait` 等待消费者腾空间；
- 同时 fsync 的频率（每次 RealFlush）不变，但每次需刷更多字节，单次 fsync 耗时上升；
- 8T 下更糟糕（0.26×）：多线程竞争 + 大 payload，两个瓶颈叠加，`max` 达 626 秒（异常样本，生产者被彻底阻塞）。

### 5.4 B3 / B8 max 达秒级 —— fsync 阻塞尖刺

B3（1T/1024B）max = 48 ms，B8（8T/1024B）max = **626 s**。根因：
- flush_mode=2 每次消费者 batch 结束都调用 `fsync`；
- 1024B 单批 buffer 数据量大，磁盘 I/O 时间长；
- SAFE 模式下某条生产者 `lg->Info` 恰好踩到 buffer 满的瞬间，等待整个 fsync 完成，这段时间全部算到该条调用的延迟上。

### 5.5 drain_ms 全部 ≈100 ms —— 测量粒度限制

`MeasureDrain` 策略是`20 ms × 连续 5 次稳定 = 100 ms` 下限。实际 drain 远小于此，此指标仅确认没有秒级队列积压，不作精确参考。

## 6. 性能评级（Roll / SAFE / 阿里云 ECS）

| 维度 | 评分 | 说明 |
|---|---|---|
| 单线程短包吞吐 | ⭐⭐⭐⭐ | ~490k ops/s，p99<4μs，满足常规业务 |
| 单线程中包带宽 | ⭐⭐⭐⭐ | 256B 时 140 MB/s，接近磁盘上限 |
| 单线程大包 | ⭐⭐⭐ | 1024B 吞吐降至 170k，受 fsync 制约 |
| 多线程扩展性 | ⭐⭐ | 16T 仅 1.36×，锁争用明显 |
| 多线程尾延迟 | ⭐⭐ | 8T p99=141μs，max 秒级，不适合低延迟场景 |
| 崩溃安全 | ⭐⭐⭐⭐⭐ | flush_mode=2，每批 fsync 保证落盘 |

## 7. 优化建议

| 优先级 | 方向 | 预期收益 |
|---|---|---|
| ⭐⭐⭐ | [`AsyncWorker`](../logs_code/AsyncWorker.hpp:19) 改 per-thread 本地 buffer（MPSC 无锁队列） | 多线程加速比 1.36× → 预计 4~6× |
| ⭐⭐⭐ | `flush_log` 改为 0（内核 writeback）或 1（fflush）| 消除 fsync 阻塞，max 尖刺消失，吞吐 ×3~×5 |
| ⭐⭐ | `RollFileFlush` 加 `setvbuf(..., _IOFBF, 1MB)` 用户缓冲 | 减少 fwrite 系统调用，p99 改善 |
| ⭐ | `MeasureDrain` 采样间隔从 20ms 降到 1ms | 报告更精确 |
